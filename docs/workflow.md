# 앱 개발 워크플로 초안

## 초기 범위

8개 스킬로 신규 앱·기능 추가·버그 수정·리팩토링을 지원하는 지침 묶음입니다. 설치만으로 스킬을 실행하는 별도 프로그램은 제공하지 않습니다. 대상 에이전트가 필요한 스킬을 호출하거나 지침을 읽고 수행하는 방식입니다.

오케스트레이터는 프로젝트 파악·스킬 선택·전달·상태·재개를 담당합니다. 단계 스킬은 해당 결과물을 만들고 완료 근거를 반환합니다. 공통 규칙은 프로젝트별 기존 정책과 도구 설정을 우선 확인합니다.

## 단계와 경계

| 단계 | 입력 | 출력·완료 판단 |
| --- | --- | --- |
| 프로젝트·규칙 확인 | 요청, 저장소, 기존 지침·설정 | 적용 규칙과 기존 구현·검증 상태 |
| 기획 | 요청과 기존 명세 | 범위·제외 사항·검증 가능한 완료 조건 |
| UX | 요구사항과 기존 사용자 흐름 | 필요한 화면·상태·조작·오류 시나리오 |
| 기술 설계 | 요구·UX·기존 구조 | 필요한 기술 결정과 구현·검증 작업 |
| 구현 | 작업 계획과 규칙 | 코드·설정·문서 변경과 작업 단위 검증 |
| 검증 | 요구사항과 구현·실행 결과 | 조건별 통과·실패·미검증 및 발견 사항 |
| 릴리스 | 검증 결과와 요청한 배포 대상 | 목표에 해당하는 실제 배포 상태·근거 |

CI 준비는 기술 설계·구현에 포함합니다. 릴리스 단계는 해당 버전의 CI 결과와 실제 배포 상태를 확인합니다. 기술 제약이 UX에 영향을 주면 먼저 확인하고, 구현 중 발견한 문제는 해당 설계로 돌아가 수정합니다.

## 공통 전달과 기록

오케스트레이션 시 [진행 규약](../skills/app-orchestrator/references/workflow-contract.md)을 사용합니다. 각 스킬은 독립 사용 시에도 목표·결과·근거·미해결 사항을 전달합니다. 기획·리뷰만 요청하면 그 범위를 넘어 구현하지 않습니다.

작업 기록은 대상 앱의 기존 명세 체계를 재사용합니다. 체계가 없을 때의 기본 위치는 `docs/changes/<change-id>.md`이며, 작은 변경은 기존 이슈나 짧은 문서로 대체할 수 있습니다. 동일 내용을 Spec Kit·OpenSpec·자체 문서에 동시에 중복 관리하지 않습니다.

상태는 `pending`, `in_progress`, `completed`, `skipped`, `blocked`로 구분합니다. 생략 이유·차단 해소 조건을 남기고, 입력·코드·설정이 바뀌면 관련 완료 근거를 다시 확인합니다.

## 공통 규칙

`project-conventions`는 규칙의 조사·적용·필요한 제안을 담당합니다. [기본 제안](../skills/project-conventions/references/defaults.md)은 기존 정책이 없을 때만 필요한 부분에 사용합니다.

커밋·PR, 범위, 코드·네이밍, 의존성, 검증, 호환성, 설정·보안, 문서 규칙을 다룹니다. 포맷·린트·테스트의 세부 규칙은 실제 설정 파일을 원본으로 사용합니다. 오케스트레이터는 각 단계에 관련 규칙을 전달하고 `verify`에서 준수를 확인합니다.

용어가 혼동되거나 중요한 결정을 정할 때는 [도메인 용어·결정 기준](../skills/project-conventions/references/domain-language.md)을 사용합니다. 실제 사용자 개념·현재 코드 이름·공개 계약을 구분하고, 필요한 기록만 대상 앱에 남깁니다.

## 전문 분야와 실패 경로

단계 선택과 함께 [작업 성격별 연결 기준](../skills/app-orchestrator/references/skill-routing.md)을 적용합니다. 외부 전문 스킬은 현재 환경의 실제 식별자·가용성·역할을 확인한 뒤 관련 범위에 사용합니다.

기술별 연결은 [스택 지침](../skills/technical-design/references/stack-guidance.md)을 따릅니다. 웹 지침은 해당 웹 작업에, React·Next.js·React Native·Expo·PostgreSQL·Supabase 지침은 실제 구성이 확인된 작업에만 선택합니다. 이 저장소가 해당 기술·외부 스킬을 자동 설치하지는 않습니다.

버그·빌드·테스트 실패는 [디버깅 기준](../skills/implement/references/debugging.md)에 따라 재현·실패 위치·가설·최소 실험·수정·회귀 확인을 연결합니다. `verify`는 완료 주장에 맞는 실제 근거와 유효한 검증 범위를 구분합니다.

## 릴리스 구분

환경·플랫폼·배포 경로·대상 버전·완료 목표를 조합합니다. 개발 배포에서 운영으로 자동 승격하거나 앱 업로드를 실제 출시로 보고하지 않습니다. 외부 심사 대기와 미검증 상태를 그대로 전달합니다.

웹·서버, 모바일, 데스크톱에 필요한 참고 절차를 제공하며 특정 공급자의 CLI나 계정은 필수로 지정하지 않습니다. 실제 서비스의 명령·조건은 실행 시점에 해당 프로젝트와 공식 자료에서 확인합니다.

## 검증 범위와 후속 시나리오

이번 초안은 구조 검증과 지침 검토 단계입니다. 수행한 확인은 다음과 같습니다.

- `skill-creator`의 형식 검사: 8개 스킬 통과
- 한국어 메타데이터, UI 설명·기본 요청문과 스킬 이름의 일치 확인
- 양쪽 마켓플레이스의 패키지 이름·경로와 8개 스킬 목록 일치 확인
- 오케스트레이터의 내부 단계 경로와 문서의 로컬 링크 확인

이 확인은 클라이언트 설치나 실제 개발 동작을 입증하지 않습니다. 아래 표는 앞으로 실행할 행동 검증 시나리오이며, 통과 결과가 아닙니다.

| 시나리오 | 확인할 동작 | 실행 상태 |
| --- | --- | --- |
| 신규 앱, 로컬 실행까지만 요청 | 최소 흐름을 설계·구현·검증하고 배포는 생략 | 미실행 |
| 기존 앱 다크모드 추가 | 기존 UI·규칙 재사용, 불필요한 DB·스택 변경 생략 | 미실행 |
| 작은 버그 수정 | 재현·수정·회귀 확인, 긴 기획서·아키텍처 도입 없음 | 미실행 |
| API·DB 필드 변경 | 호출자·기존 데이터·전환 순서 확인 | 미실행 |
| 중단 후 코드가 바뀐 작업 재개 | 영향을 받는 단계·검증만 재확인 | 미실행 |
| 개발 환경 배포 요청 | 운영으로 승격하지 않고 대상 버전·실제 동작 확인 | 미실행 |
| 모바일 테스트 빌드 업로드 | 업로드·심사·실제 출시 상태를 구분 | 미실행 |
| 필수 도구·권한 없음 | 독립 작업은 진행, 필요한 단계는 차단·조건 기록 | 미실행 |
| `verify` 단독 요청 | 리뷰 결과만 전달하고 임의 수정·배포하지 않음 | 미실행 |
| 기존 기능 삭제·명세 이름 변경 | 삭제를 누락으로 오인하지 않고 유지할 동작과 구분해 검증 | 미실행 |
| 코드에 기존 버그가 있는 기능 기획 | 관찰 동작과 의도한 요구를 구분하고 버그를 명세로 고정하지 않음 | 미실행 |
| 함수·필드 계약 변경 | diff 밖의 호출자·export·fixture·직렬화 영향 확인 | 미실행 |
| 실패한 수정이 반복되는 버그 | 새 추측을 덧붙이지 않고 원인·가설·실험 결과를 재검토 | 미실행 |
| 사용자와 코드가 같은 용어를 다르게 사용 | 의미·기존 이름 매핑을 정리하고 공개 이름 자동 변경 없음 | 미실행 |
| React·PostgreSQL이 없는 프로젝트 | 해당 스택의 전문 지침·설치를 강제하지 않음 | 미실행 |
| 실제 React·PostgreSQL 프로젝트 | 관련 전문 지침·버전·도구의 적용 범위와 역할을 확인 | 미실행 |
| 린트만 통과한 구현 | 빌드·테스트·실제 동작 전체가 성공했다고 보고하지 않음 | 미실행 |

먼저 한 클라이언트와 작은 대상 프로젝트에서 시험한 다음 결과에 따라 수정합니다. 이후 다른 클라이언트 설치와 앱별 릴리스를 확인합니다.

## 고도화 기준

- 특정 분야가 독립적으로 자주 사용되면 `technical-design`의 API·DB 등 해당 부분을 별도 스킬로 분리합니다.
- 공통 규칙을 모두 별도 스킬로 분리하거나 특정 아키텍처·스택을 초기 필수값으로 정하지 않습니다.
- 실제 반복 작업이 확인될 때 실행 도구나 상태 자동화 스크립트를 추가합니다.
- 스킬 간 전달 누락·잘못된 생략·검증 오류를 실제 사례에 근거해 개선합니다.
