# 단계 전달과 진행 기록

## 기록 위치

기록은 대상 앱 저장소에 둔다. 스킬 설치본이나 `ns_skills`에 앱별 진행 상태를 쓰지 않는다.

- 기존 Spec Kit·OpenSpec·프로젝트 계획 문서가 있으면 해당 구조를 따른다.
- 없으면 변경 단위로 `docs/changes/<change-id>.md` 한 파일을 기본으로 사용한다. 기존 기록과 겹치면 새 파일을 만들지 않는다.
- [변경 기록 양식](../assets/change-record.md)은 보관할 기록이 필요할 때 복사해서 채운다. 작은 단일 작업은 기존 이슈나 짧은 기록으로 대체한다.
- 계획·설계·테스트가 커질 때만 파일을 나눈다. 분리한 결과물은 경로로 연결한다.

## 공통 전달 항목

각 단계는 다음 정보를 전달한다. 같은 정보를 반복 복사하지 말고 기존 결과물을 연결한다.

| 항목 | 내용 |
| --- | --- |
| 목표·입력 | 이번 단계의 목표, 관련 요구사항과 앞 단계의 결과 |
| 적용 규칙 | 관련 프로젝트 규칙·설정의 출처 |
| 결과·결정 | 작성·변경한 파일, 결정 이유와 영향 범위 |
| 근거 | 완료 조건별 검증 결과나 설계의 확인 근거 |
| 남은 사항 | 미확정 사항, 차단 조건, 다음 단계가 할 일 |

적용 규칙에는 프로젝트 정책의 값·범위·출처와 필요한 미정·연기 항목을 연결한다. 기획 이후 정책 설정 결과를 받으며, 단계 진입 전에 관련 미정 정책과 연기 조건의 도래 여부를 확인한다. 정책의 상태와 개발 단계의 상태를 혼동하지 않는다.

여러 요구·작업이 얽히면 요구 ID → 변경 종류 → 작업 ID·코드 영역 → 검증 근거를 연결한다. 추가·수정은 새 동작을, 삭제는 제거할 동작을, 이름 변경은 유지할 동작을 기준으로 삼는다. 작은 작업은 한 문장으로 같은 관계를 표현할 수 있다.

## 단계 상태

- `pending`: 필요하지만 아직 시작하지 않음
- `in_progress`: 수행 중
- `completed`: 정의한 단계 결과와 완료 조건을 충족함
- `skipped`: 이번 요청에 필요하지 않음. 이유를 함께 기록
- `blocked`: 필요한 입력·환경·권한이 없어 진행할 수 없음. 해소 조건을 기록

`blocked`는 이 문서의 단계 상태이며 에이전트 제품의 목표·작업 상태 API를 변경하라는 지시가 아니다. 실패는 근거에 기록하고 수정할 작업을 `pending` 또는 `in_progress`로 되돌린다. 실패·미검증 결과를 `skipped`로 덮지 않는다.

개별 단계의 완료와 요청 전체 완료를 구분한다. 구현은 끝나도 필수 검증이 남으면 전체 완료가 아니다. 배포가 범위 밖이면 해당 단계를 생략하고 구현·검증 결과로 완료할 수 있다.

## 중단 후 재개

1. 사용자 요청과 기존 기록, 작업 트리·현재 버전, 관련 CI·외부 상태를 대조한다.
2. 완료·생략 여부를 재사용할 수 있는지 확인한다. 이전 기록만으로 현재 상태를 단정하지 않는다.
3. 바뀐 요구·코드·설정에 영향을 받는 결정과 검증을 다시 확인 대상으로 표시한다.
4. 미완료이면서 입력이 준비된 단계부터 이어간다. 다른 작업의 상태를 덮어쓰지 않는다.

정책이 바뀌었으면 관련 계획·절차·검증의 영향을 확인한다. 그대로인 정책은 기존 답과 출처를 재사용한다. 문서에 정책이 없다는 이유만으로 이미 한 결정을 다시 질문하지 않는다.

장기 작업은 의미 있는 단계 완료·변경·차단 시에 기록을 갱신한다. 모든 도구 호출을 기록할 필요는 없다.

## 실행 권한과 외부 상태

기존 사용자 지시와 권한을 이어받되 기획·구현·커밋·푸시·PR·배포의 요청 범위를 구분한다. 필수 정보가 없어 다음 외부 변경을 할 수 없을 때는 가능한 준비와 검증을 완료한 후 필요한 정보만 확인한다.

외부 심사·권한 부족 등은 실제 상태와 다음 조치를 남긴다. 기록을 남긴 것만으로 자동 감시·미래 재시도를 약속하지 않는다.
