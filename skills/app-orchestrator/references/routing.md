# 작업별 경로와 설계·구현의 일치 확인

## 실행 깊이 선택

파일 수나 기능 이름만으로 깊이를 정하지 않는다. 사용자에게 보이는 변화, 계약·데이터 영향, 되돌리기 어려움과 미확정 사항을 기준으로 정한다.

여러 작업이 독립적으로 구현되더라도 같은 API·상태·데이터 소유권·사용자 흐름을 선택해야 하면 공유 결정을 먼저 정리한다. 시각 표현과 실제 조작·상태 동작을 구분해 전달하되, 별도 문서 두 개를 의무화하지 않는다.

| 상황 | 필요한 흐름 | 줄일 수 있는 부분 |
| --- | --- | --- |
| 새 앱 | 핵심 사용자 흐름 하나의 기획·UX·기술 설계·구현·검증 | 미래 기능과 추측한 확장 구조 |
| 기존 기능 추가 | 현재 동작 확인 → 변경 요구 → 관련 설계 → 구현·검증 | 이미 검증된 스택·규칙의 재선정 |
| 작은 버그 | 재현·기대 동작 → 원인·호출자 확인 → 수정·회귀 검증 | 별도 장문 기획서와 신규 아키텍처 |
| 리팩토링 | 유지할 외부 동작 → 영향·전환 계획 → 구현·검증 | 동작 변화가 없는 새 제품 명세 |
| 계약·데이터 변경 | 호출자·기존 데이터 확인 → 전환 설계 → 구현·호환성 검증 | 영향과 관계없는 화면·디자인 작업 |

## 기존 프로젝트에서 출발

관련 진입점·공개 인터페이스·호출자·테스트를 읽고 현재 관찰한 동작을 적는다. 코드를 보고 추정한 내용은 가정으로 표시한다. **현재 동작이 곧 의도한 요구사항이라는 결론을 내리지 않는다.** 알려진 버그나 잘못된 권한 처리를 새 명세의 정상 동작으로 고정하지 않는다.

명세가 없으면 이번 변경에 필요한 기준만 복원한다. 앱 전체의 역설계를 기본 작업으로 확대하지 않는다.

## 기존 명세 체계와 연결

- Spec Kit·OpenSpec이 이미 사용 중이면 현재 변경과 실제 문서 위치를 확인한다. 다른 변경을 최근 수정 시각만으로 선택하지 않는다.
- 도구가 실제 상태·경로를 제공하면 확인된 출력과 현재 파일을 기준으로 삼는다. 예제 경로나 파일명, 체크박스 개수만으로 준비·완료를 추측하지 않는다.
- 외부 프레임워크를 쓰지 않는 프로젝트는 기존 계획 또는 가벼운 변경 기록을 사용한다. 참고 자료를 읽었다는 이유로 CLI·훅·폴더 체계를 새로 도입하지 않는다.

## 재계획과 완료 확인

요구사항 → 설계 결정 → 작업 → 구현 → 검증 근거를 필요한 범위에서 연결한다. 체크된 작업도 현재 코드가 요구를 충족하는지 확인한다.

| 차이 | 다음 행동 |
| --- | --- |
| 필요한 구현이 없음 | 관련 요구와 누락 작업을 연결 |
| 일부만 구현됨 | 남은 동작과 확인 방법을 작업에 추가 |
| 명세·설계와 충돌 | 실제 요청과 결정 이유를 확인해 관련 설계 또는 구현 수정 |
| 요청 밖의 구현 | 영향과 필요성을 설명하고 범위 조정 대상으로 분리; 임의 삭제하지 않음 |

기획 변경은 관련 UX·계약·작업·검증에, 기술 결정 변경은 관련 작업·구현·검증에 영향을 줄 수 있다. 후속 단계에서 발견한 사실도 앞 단계에 반영한다. 수정할 필요가 없는 기존 결과는 유지한다.
