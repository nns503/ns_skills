# 모바일 앱 패키징·배포

1. 플랫폼·앱 식별자, 연결할 서버 환경, 배포 경로와 목표를 확인한다. 내부 테스트·베타·정식 배포 및 업로드·심사 제출·출시 요청을 구분한다.
2. 프로젝트 설정과 현재 공식 배포 안내에서 빌드·버전 식별자, 서명·프로비저닝·계정 권한, 필요한 배포 메타데이터를 확인한다. 비밀값과 서명 자료를 저장소나 작업 기록에 복사하지 않는다.
3. 해당 앱 빌드가 올바른 서버와 설정을 사용하는지 확인한다. 대상 기기·런타임에서 관련 핵심 시나리오를 검증하고, 기존 설치의 데이터·API 호환성에 영향이 있으면 업그레이드 경로를 확인한다.
4. 요청 범위의 패키징·테스트 배포·업로드·제출·출시를 수행한다. 빌드 성공만으로 설치·출시 성공을 보고하지 않는다.
5. 패키지·빌드·배포 식별자와 실제 상태를 확인한다. 심사 대기는 심사 대기로 기록하고, 실제 출시와 출시 후 동작 확인은 별도로 보고한다.

배포된 앱을 사용자의 기기에서 즉시 모두 교체하거나 회수할 수 있다고 가정하지 않는다. 기존 앱과 서버의 공존, 필요한 업데이트 안내·배포 중지·후속 버전 등 프로젝트가 지원하는 대응을 확인한다. 외부 절차가 남으면 현재 상태와 다음 행동을 남긴다.

## 플랫폼별 확인 근거

- Android는 디버그 실행과 릴리스 구성·서명된 배포 빌드의 시험을 구분한다. 서버 설정과 관련 대상에서의 릴리스 동작을 확인한다. [Android 릴리스 준비](https://developer.android.com/studio/publish/preparing)
- Apple 플랫폼에서 TestFlight를 사용하면 빌드 업로드, 테스터 배포와 필요한 검토 상태를 구분한다. 베타 배포를 정식 출시로 보고하지 않는다. [TestFlight 개요](https://developer.apple.com/help/app-store-connect/test-a-beta-version/testflight-overview/)

기기·테스터 수, 버전 요구와 심사 조건은 실행 시점의 공식 안내에서 다시 확인한다. 이 문서는 특정 모바일 프레임워크나 배포 서비스를 강제하지 않는다.
