# 기획 구체화

사용자가 해결하려는 문제를 구현과 검증으로 이어질 만큼 구체화한다. 단독 사용 시 기획 결과를 전달하고, 요청하지 않은 구현이나 배포까지 확장하지 않는다.

## 입력과 진행

사용자 요청, 기존 제품·기능·명세와 관련 프로젝트 규칙을 확인한다. 이미 결정된 것을 다시 질문하지 않는다. 요구가 모호하거나 기존 기능을 바꾸면 [요구사항과 변경분 정리 기준](references/requirements.md)을 읽는다.

- 누가 어떤 상황에서 무엇을 해결하려는지 정리한다.
- 신규 앱은 최소한의 완결된 사용자 흐름을, 기능 추가는 기존 동작과 달라질 부분을 정의한다.
- 이번에 포함할 내용과 제외할 내용을 정한다. 버그는 현재 동작·기대 동작·재현 조건을, 리팩토링은 유지해야 할 동작을 구분한다.
- 핵심 정상 흐름과 결과에 중요한 실패·권한·데이터 조건을 적는다.
- 각 요구사항을 관찰 가능한 완료 조건에 연결한다. 예를 들어 저장 기능은 입력뿐 아니라 저장 결과와 다시 조회했을 때의 동작까지 고려한다. 근거 없는 성능·사용량 수치를 만들어 넣지 않는다.
- 기존 기능은 추가·수정·삭제·이름 변경 중 무엇인지 구분하고 유지할 동작과 전환 영향을 적는다. 코드에서 관찰한 버그를 의도한 요구사항으로 고정하지 않는다.
- 미확정 내용은 사실·가정·질문으로 구분한다. 방향이나 데이터 손실 가능성에 영향을 주는 질문을 우선하고, 나머지는 명시한 가정으로 진행한다.

## 결과와 완료 조건

목표, 사용자, 포함·제외 범위, 주요 시나리오, 완료 조건, 미확정 사항을 전달한다. 필요할 때 요구사항에 식별자를 붙여 설계·검증에서 연결한다.

작은 변경은 몇 문장과 체크리스트로 충분하다. 기존 명세가 있으면 변경분을 반영하고, 같은 내용을 새 기획서에 중복 작성하지 않는다. 구현 방식·스택은 제약이 있는 경우만 기획에 포함한다.

완료 조건으로 검증할 수 있는 범위가 정해지면 다음 단계로 넘긴다. 핵심 사용자나 목표 자체가 미정이면 그 선택을 완료된 것으로 처리하지 않는다.
