# 요구사항 구체화와 변경분 정리

목표·범위가 모호하거나 기존 기능을 바꿀 때 읽는다. 작은 요청은 아래 기준을 짧은 문장에 적용하고 별도 문서를 늘리지 않는다.

## 사용자 관점의 요구와 구현 방법 구분

요구사항은 사용자가 할 수 있는 행동, 외부 시스템이 의존하는 결과, 필요한 제약을 설명한다. 라이브러리·클래스·폴더 이름은 보통 기술 설계에 둔다. 사용자가 정한 스택과 실제 외부 계약은 제약으로 보존한다.

우선순위는 독립적으로 사용할 수 있는 사용자 흐름을 기준으로 정한다. 성능·규모 수치는 사용자 요구나 측정 근거가 있을 때 정하며, 기획서를 채우려고 임의의 목표 수치를 만들지 않는다. 출시 후 사업 지표와 구현 완료를 입증하는 조건도 구분한다.

## 모호한 내용 처리

- 범위·권한·데이터 보관·실패 시 사용자 결과·외부 의존성 중 이번 작업에 관련된 내용을 확인한다.
- 답에 따라 구현이나 검증이 실제로 달라지는 질문을 우선한다. 기존 기록으로 확인할 수 있는 내용은 먼저 조사한다.
- 안전하게 되돌릴 수 있는 선택은 가정을 명시해 진행할 수 있다. 데이터 손실이나 권한 범위처럼 임의로 정할 수 없는 핵심 선택은 해소한다.
- 질문 개수나 답변 글자 수를 고정하지 않는다. 이미 받은 답을 다시 묻지 않는다.

## 기존 요구와의 관계

| 변경 종류 | 기록할 내용 | 검증 방향 |
| --- | --- | --- |
| 추가 | 새로 가능한 동작 | 새 시나리오가 동작함 |
| 수정 | 기존 동작·새 동작과 바뀌는 조건 | 변경 조건과 유지할 기존 조건을 함께 확인 |
| 삭제 | 없앨 동작, 영향받는 사용자·호출자, 전환 방법 | 제거 대상 동작이 더 이상 제공되지 않음 |
| 이름 변경 | 이름만 달라지는지 동작도 달라지는지 | 이름만 변경이면 기존 동작은 유지됨 |

기능 요구의 이름 변경과 코드 심볼 변경은 별개다. 단순 리팩토링에 새로운 제품 동작을 만들어 넣지 않는다. 현재 코드에서 발견한 동작은 관찰 근거로 기록하고, 사용자 의도와 일치하는지 따로 판단한다.

## 완료 조건 예시

예시 상황: 기존 앱의 알림 설정 저장 동작을 변경한다.

- 조건: 로그인한 사용자가 알림을 끈 상태에서 저장한다.
- 기대 결과: 저장 성공이 표시되고 다시 열어도 꺼진 상태가 유지된다.
- 실패 조건: 저장 요청이 실패하면 성공으로 표시하지 않고 다시 시도할 수 있다.

필요하면 조건·행동·기대 결과 형식으로 시나리오를 작성한다. 기존 명세 도구가 문법을 요구하면 그 문법을 따르고, 그 외 프로젝트에는 특정 영문 키워드나 헤더를 강제하지 않는다.
