# 프로젝트 규칙이 없을 때의 기본 제안

아래 내용은 이 스킬의 기본 제안이며 이미 존재하는 프로젝트 정책이 아니다. 사용자 지시·기존 프로젝트 규칙과 충돌하지 않는 범위에서 필요한 부분만 적용한다. 영구적인 정책 변경이나 새 도구 설치는 작업 범위에 맞게 결정한다.

TDD·계획/단계 확인·테스트 종류 비율·커버리지 같은 실행 방침은 프로젝트 설정에서 적용 범위를 정한다. 이 문서는 미채택 영역의 출발점이며 명시적으로 채택한 더 엄격한 정책을 대체하지 않는다. 관련 정책이 미정이면 해당 작업 전 결정이 필요한지 먼저 분류한다.

## 기획과 범위

목표·제외 범위·관찰 가능한 완료 조건을 적는다. 기존 기능 변경은 달라지는 동작과 유지할 동작을 구분한다. 불확실한 정보를 사실로 확정하지 않고 가정과 질문으로 남긴다. 작은 수정에는 긴 기획서를 요구하지 않는다.

## 코드와 구조

- 역할과 도메인이 드러나는 이름을 사용한다. 업무 로직의 의미 없는 `a`, `b`, `data2`를 피한다. 수학식이나 짧은 지역 문맥의 관례적인 이름까지 일괄 금지하지 않는다.
- 기존 책임·의존성 구성을 따르고, 이번 요구를 구현할 만큼만 분리한다. 계층 수나 특정 아키텍처를 의무화하지 않는다.
- 기존 기능·컴포넌트·표준 기능을 먼저 검토한다. 새 라이브러리·일반화·설정 옵션은 실제 필요와 비용을 설명할 수 있을 때 도입한다.
- 관련 없는 대규모 정리와 포맷 변경은 기능 변경에서 분리한다.

## 검증

실제 설정의 검증 명령을 사용한다. 변경한 동작·중요한 오류 경로·관련 회귀를 검증하고, 테스트는 관찰 가능한 결과와 중요한 불변 조건을 확인한다. 위험이 낮은 문서·표현 수정에 구현을 복제하는 테스트를 강제하지 않는다.

검증 결과는 실행 대상·방법·결과와 함께 기록한다. 실행하지 못한 항목은 미검증으로 표시한다. 입력·코드·설정이 그대로면 충분한 기존 근거를 재사용한다.

## 호환성과 데이터

기존 API 호출자, 저장 데이터와 실제 지원 버전의 영향을 확인한다. 파괴적 변경은 전환 순서·필요한 마이그레이션·복구 제약을 정한다. 사용하지 않는 버전까지 무기한 지원하거나 추측한 미래 사용자를 위한 호환 코드를 만들지 않는다.

## 설정과 보안

환경별 설정을 구분하고 필요한 값은 예시 파일이나 프로젝트 설정 안내로 설명한다. 비밀값을 코드·커밋·문서·로그에 넣지 않는다. 변경된 입력·인증·권한 경계를 확인하되, 작은 수정에 프로젝트 전체 보안 감사를 강제하지 않는다.

## 커밋·브랜치·PR

- 커밋은 이해하고 되돌릴 수 있는 변경 단위로 나눈다. 사용자 변경을 무관하게 포함하지 않는다.
- 기존 메시지 규칙이 없으면 `feat:`, `fix:`, `refactor:`, `docs:`, `test:`, `chore:` 형태를 제안한다. 설명은 한국어로 작성한다.
- 브랜치 명명과 병합 방식은 기존 정책을 따른다. 없으면 작업 목적이 드러나는 짧은 이름을 제안하고, 실행 환경의 브랜치 규칙도 존중한다.
- PR에는 변경 이유, 달라진 동작, 검증 결과와 관련 데이터·배포 영향을 적는다. UI 변경은 필요하고 가능한 경우 화면 근거를 포함한다.
- 규칙을 확인한 것과 Git 변경 권한은 별개다. 이미 받은 권한을 재사용하되 요청 범위를 확장하지 않는다.

구체적인 커밋 형식과 PR 작성 판단은 별도 Git 협업 기준을 사용한다. 실제 Git 작업에 필요한 경우에만 해당 자료를 읽는다.

## 문서와 전달

동작·설정·실행 방법이 바뀌면 기존 관련 문서를 갱신한다. 장기적으로 중요한 기술 결정만 이유와 함께 남긴다. 이미 있는 명세나 계획을 연결하고 같은 내용을 여러 곳에 중복 관리하지 않는다.
