# 도메인 용어와 중요한 결정 기록

같은 개념에 여러 이름을 쓰거나, 사용자 표현·기획·코드의 의미가 다를 때 읽는다. 기존 용어집과 결정 기록이 있으면 먼저 확인한다.

## 용어 정리

이번 작업의 용어가 가리키는 대상·범위·생명주기를 확인한다. 예를 들어 `사용자`, `계정`, `고객`이 같은 것인지 별개인지 실제 시나리오·기존 코드·사용자 의도로 확인한다. 코드에서 발견한 의미와 합의한 의미가 다르면 차이를 드러낸다.

필요한 개념만 짧게 기록한다.

| 용어 | 의미·경계 | 기존 이름·혼동하기 쉬운 표현 |
| --- | --- | --- |
| 작업 공간 | 이 예시 앱에서 멤버와 자료를 공유하는 범위 | 코드가 project라고 부르면 현재 매핑과 변경 여부를 구분 |

이는 예시이며 프로젝트 기본 도메인이 아니다. 용어집을 일반 프로그래밍 사전이나 상세 스키마·API 명세로 키우지 않는다. 여러 업무 영역에서 같은 단어의 의미가 다르면 맥락을 함께 적는다.

새 이름을 정했다고 공개 API·DB 컬럼·코드 심볼을 일괄 변경하지 않는다. 현재 코드와의 매핑을 먼저 남기고 실제 이름 변경은 호환성·전환 범위를 확인한 작업으로 처리한다.

## 결정 기록

나중에 이유를 모르면 되돌리기 쉽거나, 여러 작업이 다르게 선택하면 충돌하는 중요한 결정만 남긴다. 실제 대안·비용·제약이 있는 판단을 우선한다. 간단한 결정은 기존 변경 기록의 한 문단으로 충분하다.

독립된 ADR이 유용하면 기존 위치·양식을 따르고, 없으면 프로젝트 문서 안에서 제목·맥락·결정·이유·관련 경로를 짧게 남긴다. 중요한 대안·영향·상태가 있을 때만 추가한다. 모든 라이브러리나 변수명에 ADR을 만들지 않는다.

용어·결정 기록은 합의한 기준이며 실제 구현·실행 결과와 구분한다. 변경이 생기면 관련 단계에 전달하고 기존 결정을 조용히 덮어쓰지 않는다. 빈 문서·폴더는 미리 만들지 않는다.
