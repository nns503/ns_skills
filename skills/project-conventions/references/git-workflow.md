# 커밋·PR 규칙 확인과 기본 제안

Git 작업을 수행하거나 해당 컨벤션을 정할 때 읽는다. 기존 프로젝트 규칙·템플릿·도구 설정이 있으면 우선 사용한다.

## 커밋

기존 규칙이 없고 Conventional Commits를 채택한다면 `type(scope): 설명` 형태를 사용한다. scope는 필요한 경우에만 사용하며, 파괴적 변경은 `!` 또는 `BREAKING CHANGE:`로 식별한다. 표시만으로 데이터·호환성 전환 설명을 대신하지 않는다.

```text
feat(notifications): 알림 설정 저장 추가
fix(settings): 저장 실패 시 성공 안내가 나타나는 문제 수정
```

메시지 언어는 프로젝트 규칙을 따르고 없으면 한국어로 제안한다. 기능·수정·문서 등 종류를 실제 변경에 맞춰 선택한다. 커밋 형식만 도입했다고 자동 버전 관리·릴리스가 설정된 것으로 간주하지 않는다.

## PR

변경 이유와 결과를 먼저 쓰고 필요한 검증·영향을 덧붙인다. 기존 템플릿이 없다면 다음 내용을 짧게 담는다.

- 해결할 문제와 달라진 사용자·시스템 동작
- 실제 수행한 검증과 결과, 중요한 미검증 사항
- 관련 요구·이슈·설계 경로
- 해당하는 경우 UI 근거, API·데이터·환경·배포 영향

작은 변경에 빈 섹션을 모두 만들지 않는다. PR 제목·설명은 최종 변경 범위를 기준으로 맞추고, 관련 없는 포맷·정리를 섞지 않는다. 브랜치·병합·필수 CI 규칙은 프로젝트에서 확인하며 임의로 바꾸지 않는다.

## 설계 근거

- [Conventional Commits 1.0.0](https://www.conventionalcommits.org/en/v1.0.0/): 커밋 형식·scope·파괴적 변경 표시
- [Google 코드 리뷰 기준](https://google.github.io/eng-practices/review/reviewer/looking-for.html): 기능 변경과 대규모 스타일 변경 분리 참고

규칙의 채택·확인과 실제 커밋·푸시·PR·병합의 실행 권한은 구분한다. 이미 받은 권한은 그대로 재사용한다.
