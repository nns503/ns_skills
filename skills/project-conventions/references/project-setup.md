# 프로젝트 정책 조회·선택·기록

신규 앱의 킥오프 이후 또는 기존 프로젝트에서 관련 규칙이 미정일 때 읽는다. 규칙 목록은 확인할 범위이며 모든 항목에 대한 인터뷰를 의무화하지 않는다.

## 순서

1. 사용자 지시, 적용 지침, 기존 정책·템플릿·도구 설정과 실제 관례를 조사한다. 기존 정책의 값·출처를 재사용한다.
2. 목표·제외 범위·위험·완료 범위를 입력으로 이번 작업에 필요한 정책을 고른다. 정보가 이미 있으면 별도 킥오프나 질문을 반복하지 않는다.
3. 누락 항목을 아래 상태로 분류한다. 정책을 결정할 정보와 실행할 권한이 있는지도 구분한다.
4. 지금 필요한 핵심 선택은 합리적인 제안과 영향을 설명해 결정한다. 답변이 필요한 선택은 기다리되 독립적으로 가능한 작업은 계속한다. 응답이 없다는 사실을 동의로 처리하지 않는다.
5. 기존 문서 또는 필요한 최소 기록에 결과를 남기고 다음 단계에 관련 값·출처·미정 항목만 전달한다.

## 정책 상태

| 상태 | 의미 | 다음 행동 |
| --- | --- | --- |
| `existing` | 기존 규칙·사용자 지시에 적용 기준이 있음 | 출처·적용 범위를 기록하고 재사용 |
| `decided` | 이번에 필요한 선택을 확정함 | 결정 근거·적용 범위를 기록하고 사용 |
| `defaulted` | 작고 되돌리기 쉬운 선택에 기본안을 적용함 | 기본값임을 명시하고 변경 가능하게 유지 |
| `pending` | 해당 작업 전에 필요한 핵심 선택이 미정임 | 관련 선택을 해소할 때까지 의존 작업 보류 |
| `deferred` | 아직 필요하지 않거나 선행 정보가 부족함 | 구체적인 결정 시점·조건 기록 |
| `not_applicable` | 이번 프로젝트·범위에 적용되지 않음 | 이유를 기록하고 해당 의무를 만들지 않음 |

이 상태는 프로젝트 정책의 상태이며 개발 단계의 `pending/completed` 등과 별개다. `pending`을 이름만 `deferred`로 바꿔 필요한 결정을 회피하지 않는다. 연기 조건이 도래하면 해당 작업 전에 다시 분류한다.

## 확인할 최소 분야

| 분야 | 지금 필요한 경우 정할 내용 | 뒤에 정할 수 있는 내용 |
| --- | --- | --- |
| 자율성·확인 | 요청 범위 안에서 자율 진행할 일, 계획·단계 확인 방식, 다시 논의할 조건 | 아직 범위 밖인 외부 작업 |
| 테스트·품질 | TDD 적용 범위, 필수 검증, 수치 목표의 필요 여부 | 스택 선택 후의 구체적인 명령·도구 |
| 구현 규모 | 기존 구조 준수, 의존성 추가·관련 리팩토링 기준 | 필요가 생기지 않은 아키텍처 선택 |
| 코드·용어 | 기존 명명·도메인·포맷·린트·타입 정책 | 기술 선정 후의 설정 파일·명령 |
| Git 협업 | 이번 Git 작업에 필요한 브랜치·커밋·PR·병합 규칙 | 당장 요청하지 않은 PR·배포 자동화 |
| 호환성·데이터 | 영향받는 기존 호출자·데이터·지원 버전·파괴적 변경 방침 | 아직 존재하지 않는 사용자·클라이언트 |
| 배포 | 요청한 환경·플랫폼·범위와 실행 조건 | 로컬 MVP 범위 밖의 운영·스토어 출시 |
| 완료 기준 | 이번 요청을 완료로 판단할 결과·필수 확인 | 관련 없는 장기 운영 지표 |

TDD는 프로젝트가 원하는 적용 범위를 정한다. 테스트 종류의 비율과 커버리지는 서로 다른 정책이며, 필요할 때 대상·측정 도구·예외까지 정한다. 명시적으로 채택한 수치를 스킬의 간단한 기본안으로 낮추거나, 미정인 수치를 임의로 만들어 넣지 않는다.

## 기록과 권한

기존 정책 문서·도구 설정을 원본으로 사용한다. 새로운 기록이 유용하면 대상 앱의 `docs/project-rules.md`에 값·범위·상태·출처·재확인 시점을 적고 기존 `AGENTS.md`에 경로를 연결한다. 전체 설정을 문서에 복제하지 않는다. 작은 기존 수정은 기존 변경 기록의 짧은 단락으로 충분할 수 있다.

기본 양식의 빈 값은 채택된 정책이 아니다. 일반적인 개발 선호, 계획 확인 절차와 커밋·푸시·병합·환경별 배포의 실제 대상·권한을 구분한다. 기존 사용자 지시와 실행 환경의 권한은 재사용하고, 정책 문서를 기록한 것만으로 요청 범위를 확대하지 않는다.

## 적용 예시

- 기존 프로젝트가 전체 TDD를 명시했다면 `existing`으로 적용한다. 레퍼런스의 위험 기반 기본안으로 대체하지 않는다.
- 새 앱에서 TDD를 위험한 로직·버그 수정에 적용하기로 했다면 그 범위를 `decided`로 기록한다. 각 작업은 해당 조건에 드는지 판단한다.
- 로컬 실행만 요청했다면 운영·스토어 배포 정책은 이유와 향후 출시 논의 시점을 남겨 `deferred`로 처리할 수 있다.
- 스택이 아직 미정이면 검증 명령은 기술 설계 완료 시점까지 연기하고, 구현 전에 실제 설정과 함께 채운다.

## 변경과 완료

선택한 정책의 원본·범위가 바뀌면 이유·영향·대체 값을 기록하고 관련 계획·검증을 갱신한다. 변경이 없으면 초기 정책 인터뷰를 반복하지 않는다.

규칙 설정 단계는 다음 작업에 필요한 핵심 선택이 해소되고 나머지가 출처 있는 기존 정책·명시한 기본값·조건부 연기·해당 없음으로 분류되면 완료할 수 있다. 미정 정책이 있는 상태를 모든 규칙이 확정되었다고 보고하지 않는다.
