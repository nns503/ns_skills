# 필요한 범위를 완결하는 구현

버그 수정, 계약·타입 변경, 재사용·의존성 판단 또는 여러 곳에 걸친 변경에 적용한다.

## 변경 전 영향 범위

관련 심볼·계약의 호출자, export, 테스트·fixture, 설정·직렬화·문서를 확인한다. 함수나 필드 이름을 바꿀 때 diff에 없는 파일도 영향을 받을 수 있다. 사용하지 않는다고 판단해 제거하려면 실제 참조·동적 등록·외부 공개 여부를 확인한다.

버그 수정은 가능한 범위에서 실패 입력과 기대 결과를 확인하고, 공통 원인이 있는 위치를 고친다. 호출자마다 같은 우회 처리를 추가하는 방식은 원인과 기존 구조에 비춰 판단한다.

## 재사용 판단

기존 프로젝트 기능과 관례를 먼저 확인하고, 그다음 표준·플랫폼 기능, 이미 설치된 의존성, 필요한 새 구현을 검토한다. 이 순서를 따랐다는 이유만으로 요구를 충족하지 못하는 기능을 선택하지 않는다.

짧아 보이는 diff보다 필요한 호출자·데이터·검증까지 포함한 완결된 변경을 우선한다. 기존 코드에서 가져온 오류 처리·입력 검증·권한·접근성을 단순화 과정에서 누락하지 않는다. 줄 수를 줄이기 위해 이해하기 어려운 한 줄 코드로 바꾸지 않는다.

## 작업과 진행 표시

작업 시작 전에 관련 요구·설계·확인 방법을 읽는다. 작업을 수행하고 필요한 검증·문서를 함께 처리한 뒤 완료를 기록한다. 체크박스만 바꾸거나 문서의 완료 표시를 실행 근거로 쓰지 않는다.

부분 구현이면 끝난 부분과 남은 부분을 구분한다. 계획 밖의 필요가 발견되면 기존 요청과 연결되는 필수 수정인지 새 범위인지 밝힌다. 외부 차단과 설계 문제를 숨기지 않는다.
