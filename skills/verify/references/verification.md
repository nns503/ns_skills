# 요구사항 검증과 근거 있는 리뷰

명세·작업 목록이 있거나 변경 종류·영향이 복잡할 때 관련 기준을 읽는다. 검증 항목 수를 늘리는 것보다 실제 완료 판단에 필요한 근거를 모은다.

## 구분해서 확인

1. **완결성:** 필요한 요구·작업이 빠지지 않았는가. 작업 체크만으로 코드가 있다고 단정하지 않는다.
2. **동작:** 정상·실패·권한·경계 조건이 의도한 결과를 만드는가. 테스트가 실제 결함을 잡을 수 있는지도 읽는다.
3. **일관성:** 요구·기술 결정·구현과 기존 계약·프로젝트 규칙이 맞는가.

명세가 이번 작업에 불필요한 경우와 필수 명세를 읽을 수 없는 경우를 구분한다. 후자는 미검증이며 통과가 아니다. 테스트 파일이 존재하는 것과 실제 실행해 통과한 것도 구분한다.

## 완료 주장과 근거의 범위

검사 명령·종료 상태·출력과 대상 코드·입력·환경을 확인한다. 실패 출력을 무시하거나 검사를 줄여 이전과 같은 성공인 것처럼 표시하지 않는다.

| 주장 | 필요한 근거 |
| --- | --- |
| 빌드 성공 | 해당 버전의 실제 빌드 결과 |
| 테스트 통과 | 실행한 테스트 범위와 실제 결과 |
| 버그 수정 | 원래 재현 조건의 결과와 필요한 회귀 확인 |
| 요구 충족 | 요구·시나리오별 구현·실행 근거 |
| 배포 동작 확인 | 대상 버전·환경과 실제 서비스·앱의 관련 동작 |

같은 입력·코드·환경의 유효한 결과는 재사용하고, 바뀐 부분에 영향을 받는 검증만 다시 수행한다. 매 응답마다 전체 검사를 반복하는 것은 이 기준의 요구가 아니다.

## 변경 종류에 맞는 검증

| 변경 | 확인 기준 |
| --- | --- |
| 추가·수정 | 새 요구의 동작·오류와 유지할 기존 동작 |
| 삭제 | 기존 동작과 호출자를 파악한 후 제거 대상이 더 이상 제공되지 않는지 확인 |
| 이름 변경 | 이름만 바뀌면 기존 동작 유지; 기능 명세 이름만 바뀌었다고 코드 심볼 변경까지 요구하지 않음 |
| 리팩토링 | 유지하기로 한 결과·외부 계약·데이터 동작이 그대로인지 확인 |

삭제 대상을 찾지 못한 것만으로 삭제 성공이라고 판단하지 않는다. 어떤 기존 동작을 제거하는지 확인할 근거가 없으면 미검증으로 남긴다. 삭제한 기능을 누락 구현으로 분류해 다시 만들라고 권하지 않는다.

## 리뷰 범위와 발견 사항

호출자·피호출자·데이터 흐름을 따라 실제 영향을 확인한다. 문서·설정에 근거한 예상 사용량으로 동시성·성능·자원 위험을 판단하고, 규모를 모르면 가정을 밝힌다.

발견 사항은 `조건 → 잘못된 결과 → 사용자·운영 영향 → 관련 위치·근거 → 필요한 수정`으로 설명한다. 재현이나 코드 경로로 뒷받침되지 않은 우려는 확정된 결함으로 보고하지 않는다. 요구 위반·결함과 스타일 취향을 구분한다.

웹 UI는 실제 렌더링 상태에서 조작하고 기대 동작을 확인한다. 도구를 쓸 때는 관찰한 요소를 대상으로 조건 대기·단언을 사용한다. 스크린샷만으로 저장·권한·데이터 정합성을 입증하지 않는다.

위 내용을 한국어로 재구성한 자체 검증 기준이다. 필수 테스트 수·커버리지 비율·고정 리뷰 문구를 추가하지 않는다.
